# Mobile location read API

ROLE: APP · DOC-REV: 2.0.0. This consumer read extension connects the Android map to the updated INTEGRATION `IntegrationStore` and MEC `Location` events. It does not change the team's policy or mutation routes. The [wire contract](../../app/contracts/mobile-location.v1.json) requires integration-owner review before a central release.

`GET /v1/keyrings` returns only keyrings explicitly bound by the server administrator to the cryptographically verified OIDC subject. The Android repository requires the response contract header, bounded JSON schema and HTTPS. It does not request phone GPS permission or infer a keyring position from RSSI.

## Authentication and authorization

- Configure a trusted HTTPS issuer, exact audience and either an RSA public key or a local JWKS. RS256 signatures, `iss`, `aud`, `sub`, required `exp`, optional `nbf`/`iat`, and `location:read` scope are checked. Missing configuration fails startup. A JWT's `jku`, `jwk`, `x5u`, algorithm override or caller-supplied principal is never trusted.
- The bindings file contains `id`, `name`, authoritative `ueId`, and explicit `principalIds`. It is reread on every request, so removing a principal removes its keyring from the next response. `active:false` returns a coordinate-free `denied` state to an otherwise bound principal.
- A binding may additionally name `grantId`. In that case the actual store grant must belong to the authenticated principal, include `location:read`, and have active, unexpired, revision-matching consent. Both grant and consent must identify the bound `ueId`, or the explicit administrator-configured `grantSubjectId` when the service uses a separate canonical device ID. Revocation, expiry or mismatch returns no coordinates or location timestamps. An owner binding without `grantId` is an explicit administrator-provisioned access decision; it does not claim to implement the app's consent UI.
- The upstream portable `/v1` mutation runner decodes claims and accepts asserted mTLS metadata. This read adapter does not use that authentication path. Keep the mutation runner private and supply MEC events through an authenticated, administrator-controlled ingress. This adapter alone does not harden the entire upstream deployment.

No CORS wildcard is emitted. Responses include `Cache-Control: no-store, private` and are never cached by the Android repository. Auth errors are 401/403; missing or malformed state is 503 without internal paths or tokens in the response. Other methods are 405 and unknown paths, including query-parameter variants, are 404.

## Location meaning

Only actual stored `service: "Location"` events with matching `ueId` are candidates. The event's `location` or `position` object supplies numeric `lat` and `lon`, optional `accuracyMeters`, and optional `expiresAt`; `observedAt` may be on the event or point, otherwise the team's event `timestamp` is used. `receivedAt`, if absent, also uses that timestamp. This fallback is a trace of the upstream contract and does not prove a physical sensor timestamp.

The newest valid observation timestamp wins over out-of-order older callbacks. Invalid coordinates in the latest observation, impossible calendar dates, future times, inconsistent receive times or invalid accuracy produce `unavailable`; an older fresh fix is not substituted. A later undatable event also prevents reuse of an earlier fix until a later valid observation supersedes it.

Freshness expires at the earlier of upstream expiry and observed time plus the configured freshness window (default 300 seconds). Expired, otherwise valid fixes remain `stale`, with their original observation time. `denied` and `unavailable` clear all coordinates and location timestamps. Battery and connectivity remain unknown unless the actual event provides valid explicit fields. No sample keyring or coordinates are generated by the API.

## Run within the workspace

Use the workspace Node installation and keep trusted configuration under `$WORKSPACE/.local/mobile-api/`. Copy the example bindings file there and replace its identifiers with real provisioning data. The example starts disabled. Configure an actual signing public key or trusted JWKS from your identity service; never commit private keys or access tokens.

```sh
export PRIVACY_BUBBLE_MOBILE_STATE_PATH="$WORKSPACE/github_upload/bubble_lock/pc-mobius/integration/state/runtime.json"
export PRIVACY_BUBBLE_MOBILE_BINDINGS_PATH="$WORKSPACE/.local/mobile-api/bindings.json"
export PRIVACY_BUBBLE_MOBILE_ISSUER="https://your-trusted-issuer.example"
export PRIVACY_BUBBLE_MOBILE_AUDIENCE="privacy-bubble-api"
export PRIVACY_BUBBLE_MOBILE_PUBLIC_KEY_PATH="$WORKSPACE/.local/mobile-api/signing-public.pem"
# Alternatively set PRIVACY_BUBBLE_MOBILE_JWKS_PATH and leave PUBLIC_KEY_PATH unset.
"$WORKSPACE/.local/node/bin/node" pc-mobius/mobile-api/server.mjs
```

The server binds only `127.0.0.1`, default port 8787 (`PRIVACY_BUBBLE_MOBILE_PORT`). Put it behind an authenticated production HTTPS reverse proxy with valid public trust, TLS 1.3, request/header/time limits and rate limiting. It never opens a public HTTP listener or modifies device/browser trust. The mobile origin must be provisioned to the app; default release traffic requires HTTPS. Debug alone may explicitly use `http://127.0.0.1:8787` through ADB reverse for controlled device tests.

The team's portable mutation runner also defaults to 8787. If both processes are needed, keep that runner private on a different loopback port (for example `PRIVACY_BUBBLE_INTEGRATION_PORT=8788`) and give the read service the same actual state-file path. Expose only the hardened read route through the mobile HTTPS origin. From `pc-mobius/`, `npm run mobile:api` starts this reader and `npm run test:mobile` runs its isolated tests.

`PRIVACY_BUBBLE_MOBILE_MAX_AGE_SECONDS` sets a freshness window from 1 to 86,400 seconds. State reads are bounded to 16 MiB/20,000 events; bindings to 128 KiB/1,000 entries/100 keyrings per principal; response body to 65,536 bytes. Lists exceeding configured bounds fail closed instead of silently dropping a keyring. There is no pagination in v1. Existing upstream file writes are not atomic; an in-progress or invalid read returns 503 and can be retried by the app. A production service owner should supply a transactional read model and signing-key rotation process appropriate to its deployment.

## Verification

```sh
"$WORKSPACE/.local/node/bin/node" --test pc-mobius/mobile-api/mobile-api.test.mjs
```

These tests use generated test signing keys and explicit location fixtures, including the actual team `IntegrationStore`/`MecCallbackIngress` classes. They cover signature/issuer/audience/scope/expiry rejection, cross-principal isolation, unknown/invalid/out-of-order/stale data, grant/consent revocation, bounds, no-store and HTTP routes. Fixture positions are test evidence, not observations of a physical keyring or a production identity-provider login.
